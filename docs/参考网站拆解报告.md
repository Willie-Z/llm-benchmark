## 0. 核心结论（一句话）

**这个网站就是领导口中的"先做的那件标准的事"的完整实现**——它已经把"规格 + 能力 → 官方参数基线 → 测试用例 → 判定 PASS/FAIL/INC/SKIP → 验收卡"整条链路跑通了。我们要做的不是从零建基线（我之前跑偏了），而是**拆解它、对齐它、然后扩展"按客户测试标准生成新用例"的能力**。

## 1. 网站是什么

- **标题**：`LLM 验收控制台 · Specifications / Capabilities`（规格 / 能力 在线验证）
- **性质**：带后端的真实系统，不是纯前端 demo
  - 前端：单页 HTML（已存 `llm_console.html`，26KB）
  - 后端：`https://kspmas.ksyun.com`（金山云），前端调 `/api/plan`（出用例）+ `/api/runs`（出结果）
  - API Key 留空 → 走服务器 `.env` 的 `LLM_API_KEY`；填写则覆盖
- **三个 Tab**：发起测试（launch）/ 进行中（running）/ 已完成（done）；进行中页每 5 秒轮询 `/api/runs`

## 2. 它如何对应领导的"两阶段"

| 领导原话 | 网站对应 |
|---|---|
| "规范、规格加能力" | 两大测试组：**Specifications（9）+ Capabilities（18）= 27 用例** |

## 3. 数据模型拆解（最关键部分）

### 3.1 基线 CATALOG（前端硬编码）
```
vendor → series → versions → {protocols, maxOutput, rpm, tpm}
例：智谱/GLM-5系列/GLM-5.2 → {protocols:[openai], maxOutput:131072, rpm:500, tpm:1000000}
```
**这正是"以官方为标准"的基线数据**。我之前从各家官网爬的 5 个基线 JSON，本质和它等价——但网站这套是它自己已固化的版本。

### 3.2 测试用例（`/api/plan` 返回 27 个，结构完整）
每个用例字段：
| 字段 | 含义 | 示例 |
|---|---|---|
| `id` | 用例标识 | `spec_context_window` |
| `group` | 组：Specifications / Capabilities | `Specifications` |
| `priority` | P0(15) / P1(12) | `P0` |
| `profiles` | 执行档：full / standard / smoke | `[full, smoke, standard]` |
| `name`/`desc` | 中文名称 + 描述 | "上下文窗口" |
| `requirement` | **测试要求**（领导说的"标准"） | "最大上下文窗口：窗口内接受，full档记录越界观察" |
| `expected` | **期望结果 + 判定规则** | "HTTP 200且含CONTEXT_OK→PASS；无哨兵→INCONCLUSIVE；失败→FAIL" |
| `run` | 后端测试函数名 | `test_context` |
| `refs` | **官网引用链接**（以官方为标准的凭证） | GLM-5.2产品说明 + Function Calling文档 |
| `source` | 来源标记 | `info.text` |

> ⭐ `requirement + expected + refs` 三件套 = 领导说的"测试标准 + 以官方为标准"。这是拆解最有价值的部分。

### 3.3 判定状态（4 态，与领导/我的设计一致）
`PASS / FAIL / INCONCLUSIVE / SKIP` —— 网站实际 run 的计数印证：
- glm-5.2 (openai, full)：PASS 22 / FAIL 2 / INC 2 / SKIP 2
- deepseek-v4-pro (anthropic, full)：PASS 21 / FAIL 0 / INC 2 / SKIP 5
- deepseek-v4-pro (anthropic, full)另一次：PASS 16 / FAIL 1 / INC 2 / SKIP 5

### 3.4 运行结果（`/api/runs` 字段）
```
run_id, metadata{model, api_format, endpoint, profile, rpm_limit, tpm_limit,
                 max_output_tokens, force_128k_output, host, started_at, ended_at},
counts{PASS,FAIL,INCONCLUSIVE,SKIP}, running, returncode
```
端点实测：`https://kspmas.ksyun.com/v1/chat/completions`(openai) 与 `/v1/messages`(anthropic)。

## 5. 它与"满足领导要求"的差距（要做的扩展）

| 能力 | 网站 | 我们要满足领导 |
|---|---|---|
| 官方参数基线 | ✅ 已有(CATALOG + refs) | ✅ 复用 + 用我爬的基线补全/校对 |
| 27 个标准用例 | ✅ 已有(/api/plan) | ✅ 直接复用为"标准用例" |
| PASS/FAIL/INC/SKIP 判定 | ✅ 已有 | ✅ 复用判定框架 |
| 多协议(openai/anthropic) | ✅ 已有 | ✅ 复用 |
| profile 档位(smoke/standard/full) | ✅ 已有 | ✅ 复用 |
| **按"客户测试标准"生成新用例** | ❌ 无 | ⬅ **核心缺口，领导明确要的** |
| 多路 Endpoint 对比(原 PRD) | ❌ 单端点 | ⬅ 原 PRD 的方向A需求 |

**核心结论**：网站把"以官方为标准的验收"做完了；领导要的"增量"是 **①按客户测试标准动态生成新用例**，**②（原 PRD 的）多路 Endpoint 并排对比**。这两点是参照该网站要补的。
