## 0. 文档说明
本PRD具体说明Endpoint验收对比工具具体解决内容以及如何实现，对应以下内容：
- 需求文档原文：多路Endpoint一致性对比
- 后续要求补充：官方参数对齐验证、各模型按各自官方信息建基座、产出可读验证卡、不笼统跑分


本 PRD 落在做什么和怎么实现，对应两条来源：
- 需求文档原文：多路 Endpoint 一致性对比，记为方向 A。
- 补充要求：官方参数对齐验证，各模型按各自官方信息建基座，产出可读验证卡，不笼统跑分，记为方向 B。

二者融合为同一工具：每路 Endpoint 各跑一次官方对齐验证，再多路并排对比一致性。最终产出一个像参考站点那样能跑且出验证卡的网站。
---

## 1. 核心业务目标

建设一个前端网站，允许用户在同一界面选择同一/不同模型，并分别为多路通道配置不同的API访问路径（Endpoint）与密钥（API Key）。向多路Endpoint发送**相同的Prompt和超参数**，直观对比各路接口在**返回参数、响应性能、文本内容行为**上是否一致；同时，每路独立对照**该模型官方参数基线**做对齐验证，逐项产出验证卡。

总结：**多路并排对比 + 每路官方对齐验证，看清问题所在。**

---


## 2. 三条不可让步的原则
1. **不笼统跑分**，每项参数独立验证，并非简单运行几个Benchmark。
2. **各模型按各自官方信息建基座**，GLM不公布MMLU就不测MMLU，DeepSeek有就测；基线各自独立，不强套统一模板，不浪费token。
3. **产出可读卡片**，每模型/每路一张卡，采用✅❌⚠️标注，不堆砌原始数据。

## 4. 功能模块

### 模块一：多路配置工作台

**模型选择**：常用模型列表（gpt-4o、claude-3.5-sonnet、deepseek-v4、glm-5.2、minimax-m3、kimi-k2.7、mimo-v2.5等）。选定模型后自动关联其官方基线（见模块二）。

**多路对比卡片**：动态增减对比通道，最少2路、建议最多4路。每路独立配置以下内容：
- Base URL/Endpoint（官网直连/中转API/自建网关）
- API Key（密码明文 隐藏/显示切换，仅存浏览器，不上传）
- API 协议格式（OpenAI/Anthropic，按模型支持项给出）
- 自定义 Headers（非必填，用于特殊网关校验）

**全局超参数**：统一配置Temperature、Top_p、Max_Tokens等，确保测试变量唯一。
> 协议与基线约束：如Kimi K2系列不暴露采样参数、MiMo 思考模式强制覆盖temp/top_p，这些项对应通道自动标SKIP，避免误判。


### 模块二：官方参数基线（自动加载）
选定模型→框架**自动加载该模型官方参数基线**（已建5家：deepseek/zhipu/minimax/kimi/mimo，存 `baselines/*.json`，聚合为 `catalog.json` 供前端直接用，每条带官网来源，**官网未公布**项标NOT_PUBLISHED）。基线驱动后续每个用例的expected期望值。
- 基线**各自独立**，不强套统一模板。
- 基线含：上下文、最大输出、temp/top_p范围与默认、功能开关（流式/工具/视觉/思考/system prompt）、限速口径、价格。
- 限速口径各家不同已全部补齐：DeepSeek=并发数(500/2500)、智谱=并发数(已登录补全,如GLM-5.2=10)、MiniMax=档位(200RPM/10M TPM)、Kimi=充值档(Tier0-5)、MiMo=RPM100/TPM10M。

### 模块三：标准测试用例

**3.1 标准用例（27 条，直接复用参考站点 `/api/plan` 结构）**
每条用例字段：`id / group(Specifications|Capabilities) / priority(P0|P1) / profiles(smoke|standard|full) / name / desc / requirement(测试要求) / expected(期望+判定规则) / run(测试函数) / refs(官网引用)`。

- **Specifications（9）**：文本IO、上下文窗口、最大输出参数、max_completion_tokens、实际生成、请求参数边界、错误信息返回、鉴权安全、线上观测字段。
- **Capabilities（18）**：思考开/关、多轮对话、思考力度、流式、函数调用、流式工具、工具鲁棒性(无误触)、结构化输出、JSON Schema、多模态输入、Partial Mode、工具选择模式、并行工具、工具错误恢复等。
- **profile 三档**：smoke（快速冒烟，≈4K）/standard（标准，≈64K）/full（全量，≈999K + 越界观测），按token预算与时间取舍。


**3.2 客户测试标准 → 生成新用例（核心扩展点）**- 输入：客户提供的测试标准（自然语言/表格）。
- 生成：按基线 + 四类对齐维度，产出符合上述结构的用例（含expected/refs）。
- 定位：参考站点目前**无此能力**，这是本工具相对参考站点的**核心增量**。

### 模块四：执行与判定

- **四态判定**：PASS（对齐）/FAIL（未对齐）/INCONCLUSIVE（官网未公布，无法判定）/SKIP（该模型该项不适用）。
- **四类对齐维度**：
  - A 能力存在性：官方支持→星流是否支持
  - B 参数边界一致性：超界传值是否与官方同样拒绝
  - C 默认值一致性：不传时默认值是否一致
  - D 参数生效一致性：合法传值行为是否一致（含思考模式覆盖）
- 执行调度：尊重每路限速口径（DeepSeek 并发数 / MiniMax 档位 / Kimi 充值档 / MiMo RPM·TPM / 智谱并发数），避免触发限流。

### 模块五：验证卡与多路对比

**5.1 单路验证卡**
```
模型: glm-5.2 · 通道: 星流中转 · 基线版本 2026-07-16 · 整体 ⚠️ 部分对齐
规格(9):  ●●●●●●○○●   能力(18): ●●●●●●●○●●●●●●○●●●
─ ✅ 文本IO  ✅ 上下文    ❌ 最大输出(星流默认≠官方)  ⚠️ 数值限速(官网未公布)
─ ✅ 流式    ✅ 函数调用  ❌ 思考模式关闭(未生效      ⏭️ 视觉(文本模型不适用)
明细可展开看expected vs 实测+官网refs链接
```

**5.2 多路并排对比表**
同一用例、N路并排，查找问题：
| 用例 | 路1官网直连 | 路2中转API | 路3自建网关 | 是否一致 |
|---|---|---|---|---|
| 最大输出 | ✅128K | ⚠️64K | ✅128K | ❌ 路2缩水 |
| 函数调用 | ✅ | ✅ | ❌未生效 | ❌ 路3缺失 |

## 8. MVP 路径

**第一步：1个模型×1路×标准用例，打通全链路**
- 选glm-5.2（或 deepseek-v4-pro），填星流Endpoint+Key，跑smoke档，出第一张验证卡。
- 目的：验证基线schema、用例结构、判定逻辑够不够用，**先验证设计，再铺量**（避免返工）。


**第二步：扩展到 1 模型 × 多路对比**（方向A 打通）
**第三步：扩展多模型**（基线各自独立，逐家上）
**第四步：客户标准→生成用例**（核心扩展）
