## 1. 需求背景

### 1.1 问题描述

星流作为 LLM 聚合平台，向客户提供多路模型 Endpoint（官网直连 / 中转 API / 自建网关）。当前验收面临以下痛点：

1. **一致性黑盒**：同一模型经不同通道出口，返回参数、性能、文本行为是否一致，缺乏逐项对比手段，问题定位靠人肉试。
2. **对齐无标准**：通道是否与官方参数对齐，没有官方基线做"标准答案"，"最大输出缩水""思考开关未生效"这类问题测不出来。
3. **笼统跑分无用**：现有验收多是跑几个 Benchmark 出个总分，看不出哪一项参数没对齐，无法指导修复。
4. **基线各家不同**：五家厂商限速口径、定价结构、参数暴露程度各不相同（DeepSeek/智谱用并发数，Kimi/MiniMax/MiMo 用 RPM/TPM；Kimi K3 采样参数强制覆盖，MiMo 思考模式强制覆盖 temp/top_p），强套统一模板会丢参数、跑不通。
5. **用例不可扩展**：参考站点有 27 条标准用例，但客户自带测试标准时无法自动转成可执行用例，人工改写慢。

### 1.2 目标用户

- **验收工程师**：负责通道上线前验收，需要逐项出验证卡、定位不对齐项。
- **模型选型人员**：对比同一模型多路通道，挑返回最对齐、最稳定的通道接入。
- **客户技术对接**：客户给测试标准，需要快速转成用例并跑出结果交付。
- **运维 / 网关负责人**：排查自建网关是否丢参数、是否缩水。
- **产品 / 决策层**：看整体对齐率与多路一致性，做通道准入决策。

### 1.3 业务目标

**核心目标**：把"多路通道是否与官方对齐、多路之间是否一致"这件事，从数小时人肉试压成 15 分钟内出可读验证卡。

**量化指标**：
- 验收效率：单路验收从平均 2 小时缩短到 15 分钟以内。
- 对齐覆盖度：单模型可验证参数项从笼统 1 个总分细化到 27+ 项逐项判定。
- 多路对比：同一用例 N 路并排，一致性判定全覆盖。
- 基线准确度：五家基线官网公开部分 100% 核实，未公布项正确标 NOT_PUBLISHED（不编造）。
- 客户标准转化：客户测试标准→可执行用例，生成准确率达 90%+（人工抽检）。

## 2. 产品定位

### 2.1 产品定义

本工具是一款面向 LLM 聚合平台的**多路 Endpoint 验收对比工具**，通过"官方基线对齐验证 + 多路并排对比"双能力，自动化完成"选模型→配通道→跑用例→出验证卡→多路对比"的完整验收流程。采用纯前端方案，直连公司现有后端，不新建后端。

### 2.2 核心价值

1. **官方对齐验证**：每路通道独立对照该模型官方参数基线，逐项出四态判定（PASS/FAIL/INC/SKIP）。
2. **多路并排对比**：同一用例 N 路并发，横向看一致性、纵向看官方对齐。
3. **基线各自独立**：五家按各自官方信息建基座，不强套统一模板，不丢参数。
4. **可读验证卡**：每路一张卡，✅❌⚠️⏭️ 标注，不堆砌原始数据。
5. **客户标准生成用例**：客户给标准，LLM 据基线+四类对齐维度生成结构化用例（参考站点无此能力）。

### 2.3 产品差异化

| 对比维度 | 传统 Benchmark | 参考站点（公司自有） | 本工具 |
|---|---|---|---|
| 验收粒度 | 笼统总分 | 27 用例逐项判定 | 27 用例 + 客户标准扩展 |
| 官方对齐 | 无基线 | 有基线但较简 | 五家 v2 基线带官网来源+核实备注 |
| 多路对比 | 无 | 单路跑测 | N 路并排一致性对比 |
| 基线口径 | 统一模板 | 统一模板 | 各家独立（并发数/RPM·TPM/充值档） |
| 未公布项 | 强行测或漏测 | 部分 | NOT_PUBLISHED→INC，不编造 |
| 用例扩展 | 人工 | 无 | LLM 按客户标准生成 |

### 2.4 大模型优势

| 维度 | 传统方案局限 | 大模型优势 |
|---|---|---|
| 用例生成 | 人工按客户标准逐条改写，耗时且易漏维度 | 理解客户自然语言标准，按四类对齐维度+基线自动生成结构化用例 |
| expected 推导 | 人工查官方文档填期望值 | 据基线字段自动填（超界→FAIL、未公布→INC、不适用→SKIP） |
| refs 关联 | 人工贴官网链接 | 从基线 sources 自动带官网引用 |
| 报告可读性 | 原始数据堆砌 | 验证卡摘要+进度点+可展开明细 |
| 多路归因 | 人工比对找差异 | 同一用例 N 路并排，自动标"路2缩水""路3缺失" |

## 3. 用户故事

> 本版块基于产品定位和参考站点已有功能反推：产品定位→用户画像，功能设计→用户故事。

### 3.1 验收工程师的逐项验收需求

**作为** 一名验收工程师
**我希望** 能为某通道填入 Endpoint 和 Key，自动跑出逐项四态判定的验证卡
**以便于** 我定位通道在哪一项参数上未与官方对齐，指导修复

**验收标准**：
- 选定模型后自动加载该模型官方 v2 基线（如 glm-5.3）。
- 跑 27 条标准用例，逐项出 PASS/FAIL/INC/SKIP。
- 验证卡可展开看 expected vs 实测 + 官网 refs 链接。
- 思考开关、采样参数等基线约束项自动标 SKIP（如 GLM-5.3 强制思考无法关闭→思考开关项 SKIP）。

**技术实现**：基线加载器→用例执行→四态判定→验证卡渲染。

### 3.2 模型选型人员的多路对比需求

**作为** 一名模型选型人员
**我希望** 同一模型配多路通道并排跑同一用例
**以便于** 我挑返回最对齐、最稳定的通道接入

**验收标准**：
- 工作台支持 2-4 路通道，各路独立配 BaseURL/Key/协议/Headers。
- 全局统一超参，保证多路发同一份。
- 出多路对比表，横向标一致性、纵向标官方对齐。
- 限速口径各异时自动节流，不触发限流。

**技术实现**：多路并发调度→轮询各路 run→聚合对比表。

### 3.3 客户技术对接的用例生成需求

**作为** 一名客户技术对接
**我希望** 客户给的测试标准能自动转成可执行用例
**以便于** 我快速交付验收结果，不用人工逐条改写

**验收标准**：
- 输入客户测试标准（结构化表 + 自然语言）。
- 选定目标模型后，结合基线 + 四类对齐维度生成用例（含 expected/refs）。
- 生成用例可单独跑或随 27 条一起跑。
- 生成结果可人工审核修改。

**技术实现**：用例生成 Agent（LLM）→四类对齐维度模板→基线驱动 expected→并入用例树。

### 3.4 运维的网关排查需求

**作为** 一名运维
**我希望** 对比官网直连与自建网关两路
**以便于** 排查网关是否丢参数、是否缩水

**验收标准**：
- 路1 官网直连、路2 自建网关，同一用例并排。
- 最大输出、函数调用、思考模式等项自动标"路2缩水""路3缺失"。
- 明细可展开看具体差值（如 ✅128K vs ⚠️64K）。

**技术实现**：多路对比表→逐项差异标注→明细展开。

### 3.5 决策层的整体看板需求

**作为** 一名决策层
**我希望** 看各通道整体对齐率与多路一致性
**以便于** 做通道准入决策

**验收标准**：
- 每路验证卡顶部摘要（整体 ⚠️ 部分对齐 · 规格 ●●●○○ · 能力 ●●●●●）。
- 多路对比表一致性列一眼看出哪路有问题。
- 计数徽章 PASS/FAIL/INC/SKIP。

**技术实现**：验证卡摘要+计数→多路对比表一致性列。

## 4. 模型故事

> 在传统 PRD 中用"用户故事"描述用户需求；在 AI 产品 PRD 中，用"模型故事"描述 Agent / 工作流节点的需求。
> 格式：作为 [角色]，在 [场景] 下，为了 [目标]，我需要 [上下文/工具/能力/约束]。
>
> **重要说明**：本工具不是多 Agent 系统，真正调用 LLM 的只有"用例生成"一环（§4.1）。其余模块（基线对齐判定、多路调度、验证卡渲染）是确定性逻辑，写成"工作流节点需求"（§4.2～4.4），格式与模型故事一致，便于开发团队统一理解。

### 4.1 用例生成 Agent 模型故事

#### 模型故事 1：理解客户测试标准

**场景描述**：客户提交一份测试标准（自然语言描述 + 结构化表格），我需要理解它要验证模型的哪些方面。

```
作为 用例生成 Agent
在 收到客户测试标准输入时
为了 准确理解客户要验证的参数与维度
我需要：

【上下文信息】
- 客户自然语言描述（如"验证思考开关在各种力度下是否生效"）
- 客户结构化表（如参数名/期望行为/边界值）
- 选定的目标模型 model_id（如 glm-5.3）
- 该模型的官方 v2 基线（features/reasoning_effort/thinking_mode/platform_params）

【能力支持】
- 自然语言理解能力（解析客户描述的真实意图）
- 基线读取能力（知道该模型支持哪些参数、哪些项 NOT_PUBLISHED）
- 维度映射能力（把客户标准映射到四类对齐维度 A/B/C/D）

【约束条件】
- 不能生成基线不支持参数的用例（如对 Kimi K3 测 temperature 传值→K3 强制覆盖，应生成 SKIP 用例而非 FAIL 用例）
- 不能编造官网未公布的 expected（基线标 NOT_PUBLISHED 的项，expected 判 INC）
- 必须区分"客户要验证什么"与"基线能否验证"
```

**为什么需要这些**：客户标准往往是非规范的自然语言，需要 LLM 理解真实意图；同时必须受基线约束，否则会生成跑不通或误判的用例——这正是陈哥说的"官网结果是 A，你拼 URL 跑出来也应该是 A"，基线就是那个 A。

#### 模型故事 2：生成结构化用例

**场景描述**：理解客户标准后，我需要按标准用例结构（id/group/priority/profiles/name/desc/requirement/expected/run/refs）生成可执行用例。

```
作为 用例生成 Agent
在 理解客户标准并映射到四类对齐维度后
为了 产出可被执行器跑、可被判定器判的结构化用例
我需要：

【上下文信息】
- 四类对齐维度模板（A 能力存在性 / B 参数边界 / C 默认值 / D 参数生效）
- 标准用例 schema（同 bench_plan.json 的 27 条结构）
- 目标模型基线（驱动 expected）
- 语言 locale

【能力支持】
- 结构化输出能力（严格符合用例 JSON schema）
- expected 推导能力（据基线字段填期望值+判定规则）
- refs 关联能力（从基线 sources 带官网引用）
- profile 分档能力（smoke/standard/full 按Token预算分配）

【输出要求】
生成严格符合以下 schema 的 JSON 数组：
{
  "id": "cust-001",
  "group": "Capabilities",
  "priority": "P0",
  "profiles": ["smoke","standard"],
  "name": "思考开关-力度档位",
  "desc": "验证 reasoning_effort 各档位是否生效",
  "requirement": "分别传 low/high/max，检查输出差异",
  "expected": "GLM-5.3 仅支持 low/high/max；传 none/minimal 应报错；官网结果见 reasoning_effort 字段",
  "expected_judgement": "档位生效→PASS；报错→FAIL；未公布→INC；参数不存在→SKIP",
  "run": "reasoning_effort_low_high_max",
  "refs": [{"label":"对话补全.md","url":"https://docs.bigmodel.cn/api-reference/模型-api/对话补全.md"}]
}

【约束条件】
- expected 必须引用基线真实数据，禁止凭记忆编造
- 官网未公布项 expected 判 INC，不能猜
- 基线不支持项（如 GLM-5.3 vision=false 的图像输入）判 SKIP
- 每条用例必带 refs 官网来源
- 不生成"汇总分析"这种非可执行步骤
```

**为什么需要这些**：结构化输出才能被执行器/判定器程序处理；expected 必须来自基线才能保证"标准答案"正确；refs 保证可追溯。

#### 模型故事 3：处理生成结果审核

**场景描述**：生成用例后，用户可能提出修改（如"加一条 JSON 输出用例""删掉视觉项"），我需要理解反馈并重新生成。

```
作为 用例生成 Agent
在 收到用户对生成用例的修改意见时
为了 产出符合用户期望的用例集
我需要：

【上下文信息】
- 原始客户标准
- 已生成的用例集
- 用户反馈内容
- 当前迭代轮次

【能力支持】
- 反馈理解能力（增/删/改/排序）
- 基线一致性保持能力（修改后仍符合基线约束）

【约束条件】
- 必须响应用户反馈
- 修改后仍符合用例 schema 与基线约束
- 达到最大迭代次数不再重新生成
```

**为什么需要这些**：用户是决策者，有权修改；防止死循环。

### 4.2 基线对齐判定节点需求

> 这不是 Agent，是确定性判定逻辑，但仍需定义它需要什么。

```
作为 基线对齐判定节点
在 收到单路某用例的执行结果时
为了 判定该项 PASS/FAIL/INC/SKIP
我需要：

【上下文信息】
- 该用例的 expected 与判定规则
- 该模型的 v2 基线对应字段（含 important_alignment_findings）
- 实际执行结果（返回参数/行为/错误）

【判定规则】（四态）
- PASS：实测与官方基线对齐
- FAIL：实测与官方基线未对齐（如星流默认 max_output=64K ≠ 官方 128K）
- INCONCLUSIVE：官网未公布（基线 NOT_PUBLISHED），无法判定
- SKIP：该模型该项不适用（如 GLM-5.3 vision=false 测图像输入；Kimi K3 测 temperature 传值被强制覆盖）

【约束条件】
- 必须据基线 important_alignment_findings 判 SKIP（如 GLM-5.3 思考强制 enabled→思考开关项 SKIP）
- 不能把 INC 当 FAIL（未公布≠未对齐）
- 不能把 SKIP 当 FAIL（不适用≠未对齐）
```

**为什么需要这些**：四态判定是本工具的核心，必须严格按基线+对齐发现判，避免误判。

### 4.3 多路调度节点需求

```
作为 多路调度节点
在 用户启动多路对比时
为了 同一用例 N 路并发跑且不触发限流
我需要：

【上下文信息】
- 各路通道配置（BaseURL/Key/协议/Headers）
- 各路模型的限速口径与数值（基线 rate_limits）
- 全局统一超参
- 用例集与 profile 档位

【能力支持】
- 并发调用能力（Promise.all）
- 限速节流能力（按各家口径：并发数 vs RPM/TPM）
- 轮询能力（每 5s 拉 /api/runs）

【约束条件】
- DeepSeek/智谱按并发数节流；Kimi/MiniMax/MiMo 按 RPM/TPM 节流
- 限速口径不同的通道间不能横比数值
- API Key 不出浏览器
```

**为什么需要这些**：五家限速口径三家不同，不节流会触发限流导致 run 失败。

### 4.4 验证卡渲染节点需求

```
作为 验证卡渲染节点
在 单路 run 完成后
为了 让用户一眼看出对齐情况
我需要：

【上下文信息】
- 该 run 的 counts（PASS/FAIL/INC/SKIP）
- 各用例的 expected vs 实测
- 官网 refs 链接

【能力支持】
- 摘要生成能力（整体 ⚠️ 部分对齐 · 规格 ●●●○○ · 能力 ●●●●●）
- 徽章渲染能力（✅❌⚠️⏭️）
- 明细展开能力（expected vs 实测 + refs）

【约束条件】
- 不堆砌原始数据
- 进度点直观（●○）
- 引用链接可点
```

**为什么需要这些**：可读卡片是三条不可让步原则之一。

### 4.5 人在环中审核节点需求

```
作为 人在环中审核节点
在 展示用例生成结果或研究计划给用户时
为了 让用户审核后再跑
我需要：

【展示信息】
- 生成的用例列表（name/desc/expected/refs）
- 基线约束提示（哪些项会 SKIP/INC）
- 预估耗时（按 profile）

【交互能力】
- 接收反馈（[ACCEPTED] / [EDIT]）
- 路由决策（接受→跑；修改→回生成 Agent）

【自动接受模式】
- auto_accepted_plan=true 时跳过等待
```

**为什么需要这些**：用例生成可能不准，需人工把关；API 场景支持自动接受提效。

## 5. 用户旅程

### 5.1 完整用户旅程：从选模型到出验证卡

#### 阶段 1：模型选择与基线加载（0-1 分钟）
- 用户在工作台选模型（如 glm-5.3）。
- 框架自动加载该模型 v2 基线，展示上下文/最大输出/协议/限速/功能开关。
- 基线带官网来源与核实备注，未公布项标 NOT_PUBLISHED。

#### 阶段 2：通道配置（1-3 分钟）
- 用户配 Endpoint/BaseURL、API Key（仅存浏览器）、协议（openai/anthropic）、自定义 Headers。
- 多路对比时配 2-4 路，各路独立。
- 设全局超参（Temperature/Top_p/Max_Tokens）。

#### 阶段 3：用例选择（3-4 分钟）
- 选标准 27 条（Specifications 9 + Capabilities 18）。
- 选 profile 档位（smoke/standard/full）。
- 可选：用例生成器按客户标准生成新用例并入树。

#### 阶段 4：执行与轮询（4-10 分钟）
- 启动测试，前端并发调用 /api/runs（或本地 serve.py 代理真发）。
- 进行中 Tab 每 5s 轮询，卡片实时更新计数徽章。
- 限速节流按各家口径。

#### 阶段 5：验证卡与判定（10-12 分钟）
- 单路完成→验证卡：四态徽章 + 进度点摘要 + 可展开明细。
- 官网未公布项→INC（⚠️），不适用项→SKIP（⏭️）。

#### 阶段 6：多路对比（12-15 分钟）
- 多路对比表：同一用例 N 路并排，标一致性。
- 横向（多路一致性）+ 纵向（每路 vs 官方）并存。
- 归因标注（路2缩水/路3缺失）。

### 5.2 关键用户体验设计原则

1. **渐进式信息披露**：先摘要（进度点+计数），再明细（展开 expected vs 实测）。
2. **透明化执行过程**：轮询实时更新，用户看得到跑测进度。
3. **基线约束可见**：SKIP/INC 项标注原因（如"GLM-5.3 思考强制 enabled→无法关闭对比"）。
4. **多路并排直观**：对比表一致性列一眼定位问题路。
5. **Key 不落盘**：密码框明文/隐藏切换，仅存浏览器。

## 8. 提示词设计

> 仅"用例生成 Agent"需要提示词，其余节点为确定性逻辑。

### 8.1 用例生成提示词设计策略

#### 策略 1：角色定位
- 定位：验收用例生成专家，熟悉五家模型官方参数基线与四类对齐维度。
- 强调："Only use baseline fields, never fabricate expected."

#### 策略 2：基线约束优先
- 强制读取目标模型 v2 基线的 important_alignment_findings。
- 基线 NOT_PUBLISHED 项→expected 判 INC。
- 基线不支持项（如 vision=false 测图像）→判 SKIP。
- 强制覆盖项（如 Kimi K3 采样参数、MiMo 思考模式 temp/top_p）→生成 SKIP 用例。

#### 策略 3：四类对齐维度模板
- A 能力存在性：官方支持→星流是否支持。
- B 参数边界一致性：超界传值是否与官方同样拒绝。
- C 默认值一致性：不传时默认值是否一致。
- D 参数生效一致性：合法传值行为是否一致。

#### 策略 4：结构化输出
- 严格符合用例 JSON schema，禁止自由文本。
- 每条必带 expected/expected_judgement/refs。

#### 策略 5：引用分离与来源追溯
- refs 从基线 sources 取，禁止编造 URL。
- 每条用例可追溯到官网文档。

#### 策略 6：安全约束
- 不生成危险操作用例（如删除、系统命令）。
- profile 分档控制 Token 预算。

### 8.2 完整提示词（中文版）

```
## 元信息
- 原文件位置: src/prompts/case_generator.md
- 变量名称: case_generator
- 功能模块: 用例生成 Agent - 按客户测试标准生成结构化验收用例
- 调用场景: 当客户提交测试标准、需要扩展标准27条用例时

## 提示词

当前时间: {{ CURRENT_TIME }}
---

你是星流 LLM 验收对比工具的 `case_generator` 代理，由工作流管理。
你是一位验收用例生成专家，精通五家模型（DeepSeek/智谱/MiniMax/Kimi/MiMo）的官方参数基线与四类对齐维度。

# 输入
- 客户测试标准：{{ CUSTOMER_STANDARD }}（自然语言 + 结构化表）
- 目标模型：{{ MODEL_ID }}
- 该模型官方 v2 基线：{{ BASELINE_JSON }}
- 语言 locale：{{ LOCALE }}

# 四类对齐维度（生成时覆盖）
- A 能力存在性：官方基线 features 支持→星流通道是否支持
- B 参数边界一致性：超界传值是否与官方同样拒绝（如 temp 超过基线 max）
- C 默认值一致性：不传参数时默认值是否与官方基线 default 一致
- D 参数生效一致性：合法传值行为是否一致（含思考模式覆盖场景）

# 步骤
1. 理解客户标准：解析自然语言与结构化表，识别要验证的参数与维度。
2. 读取基线约束：检查基线 important_alignment_findings，识别 SKIP/INC 项。
   - 强制覆盖项（如 Kimi K3 temp/top_p、MiMo 思考模式 temp/top_p、GLM-5.3 思考强制 enabled）→ 生成 SKIP 用例
   - 基线 NOT_PUBLISHED 项（如 GLM-5.3 绝对定价、Kimi 最大输出）→ expected 判 INC
   - 基线不支持项（如 GLM-5.3 vision=false 的图像输入）→ 判 SKIP
3. 映射四类维度：把客户标准映射到 A/B/C/D，每个维度生成 1-N 条用例。
4. 推导 expected：据基线字段填期望值与判定规则，禁止编造。
5. 关联 refs：从基线 sources 取官网 URL，禁止编造。
6. 分配 profile：按 Token 预算分 smoke/standard/full。

# 输出格式（严格 JSON 数组，禁止自由文本）
[
  {
    "id": "cust-001",
    "group": "Capabilities",
    "priority": "P0",
    "profiles": ["smoke","standard"],
    "name": "用例名",
    "desc": "用例描述",
    "requirement": "测试要求（具体到参数与值）",
    "expected": "期望值（引用基线真实数据）",
    "expected_judgement": "PASS/FAIL/INC/SKIP 判定规则",
    "run": "测试函数标识",
    "refs": [{"label":"官网文档名","url":"https://..."}],
    "alignment_dimension": "A|B|C|D",
    "baseline_constraint": "SKIP/INC 原因（如适用）"
  }
]

# 约束条件
- 只能使用基线字段，禁止凭记忆编造 expected
- 官网未公布项判 INC，不能猜数值
- 基线不支持项判 SKIP，不能强行测
- 强制覆盖项生成 SKIP 用例，不能生成会误判 FAIL 的用例
- 每条必带 refs 官网来源
- 不生成"汇总分析"等非可执行步骤
- 始终以 {{ LOCALE }} 语言输出 name/desc/requirement
```

### 8.3 输出 schema 校验

生成后由代码逻辑校验：

- profiles ⊆ {smoke, standard, full}。
- refs URL 必须在基线 sources 白名单内。

## 11. 异常处理与降级策略

### 11.1 异常场景定义

| 场景 | 现象 | 降级策略 |
|---|---|---|
| 通道限流 | 429/限速错误 | 按基线口径节流重试；超时标 INC |
| Key 无效 | 401 鉴权失败 | 标该路异常，不阻塞其他路 |
| 端点不通 | 超时/连接拒绝 | 标该路异常，提示检查 Endpoint |
| 基线未公布 | NOT_PUBLISHED | 判 INC，不编造 |
| 参数不适用 | 基线不支持 | 判 SKIP |
| 用例生成失败 | LLM 返回不符 schema | 重试 1 次；仍失败走人工录入 |
| 后端 /api/runs 不可达 | 网络问题 | 退回本地 serve.py 真发或模拟演示 |
| GitHub Pages 线上无代理 | serve.py 不在线 | 自动退回模拟演示，不报错 |

### 11.2 降级流程
```
真发失败 → 检查Key/Endpoint → 重试(限速节流) → 仍失败标异常
  → 多路时该路异常不影响其他路 → 验证卡该路标❌异常
线上无代理 → 自动模拟演示 → 明确标注"模拟数据"
```

## 15. PRD 撰写说明

### 15.1 本 PRD 与传统 PRD 的区别
- 引入"模型故事"描述用例生成 Agent 的需求（非用户故事）。
- 引入"工作流节点需求"描述确定性模块（格式统一）。
- 提示词章节独立成章（§8），因用例生成是 LLM 驱动。

### 15.2 提示词章节的重要性
用例生成 Agent 是本工具相对参考站点的核心增量，其质量取决于提示词。提示词必须强制基线约束，否则会生成跑不通或误判的用例。

- 五家 v2 基线已就绪（2026-08-31 完成，39 模型）。
- 原型已支持本地真发验收卡 + 多路对比（PR #1）。
