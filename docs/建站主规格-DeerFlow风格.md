## 1. 生成背景

### 1.1 生成对象

一个纯前端 Web 应用，1:1 复刻参考站点 `http://120.92.93.22/llm-benchmark` 的验收控制台（三 Tab、验证卡、PASS/FAIL/INC/SKIP），并叠加两个增量：①多路 Endpoint 并排对比；②按客户测试标准生成新用例。前端直连公司现有后端 API（`/api/plan`、`/api/runs`），**不新建任何后端**。

### 1.2 生成方法

用 AI 代码生成工具，按本规格喂料，分批复刻+叠加增量。所有功能依据见同目录《PRD》与《参考网站拆解报告》。

### 1.3 生成目标

| 维度 | 目标 |
|---|---|
| 形态 | 纯前端 Web 应用（React/Vue 任选） |
| 后端 | 直连公司现有后端，不新建 |
| 复刻度 | 1:1 还原参考站点 UI/交互 |
| 增量 | 多路对比 + 客户标准生成用例 |
| 安全 | API Key 仅存浏览器 |

## 2. 产品定位

### 2.1 生成目标定义

纯前端验收控制台，复刻参考站点形态，叠加多路对比与用例生成两个增量，直连现有后端。

### 2.2 核心价值

1. **复刻优先**：1:1 还原参考站点，不擅自改设计。
2. **直连现有后端**：用 `/api/plan`、`/api/runs`，不新建后端。
3. **增量明确**：只加两个能力，不重造已有。
4. **安全合规**：Key 不出浏览器。

### 2.3 与参考站点关系

| 维度 | 关系 |
|---|---|
| UI/交互 | 1:1 复刻 |
| API | 直连同一后端 |
| 基线 | 用 v2 增强版（39 模型）替代简版 CATALOG |
| 多路对比 | 新增 |
| 用例生成 | 新增 |

### 2.4 AI 生成差异化

| 维度 | 传统开发 | AI 生成 |
|---|---|---|
| 速度 | 逐模块开发 | 喂料批量生成 |
| 复刻 | 人工对照 | 喂源码 1:1 还原 |
| 增量 | 需求拆解 | 提示词驱动 |
| 一致性 | 靠规范 | 靠喂料顺序与约束 |

## 4. 节点故事

> AI 生成产物是前端应用，无 LLM 调用（用例生成 Agent 在 v2.0 落地）。用"节点故事"格式描述各功能节点需求。
> 格式：作为 [节点]，在 [场景] 下，为了 [目标]，我需要 [上下文/能力/约束]。

### 4.1 复刻节点故事

```
作为 复刻节点
在 AI 生成启动时
为了 1:1 还原参考站点
我需要：

【上下文信息】
- llm_console.html（前端源码，UI/交互/CSS 1:1 参考）
- bench_plan.json（27 用例数据契约样本）
- bench_runs.json（run 结果数据契约样本）

【能力支持】
- 三 Tab + hash 路由（#launch #running #done）
- 验证卡分组（Specifications/Capabilities）
- 四态徽章（✅❌⚠️⏭️）+ 进度点摘要
- 进行中 5s 轮询

【约束条件】
- 复刻时不擅自改设计
- 配色复刻 CSS 变量（--bg/--accent/#C96442）
```

**为什么需要这些**：复刻是基底，必须 1:1 才能保证与参考站点行为一致。

### 4.2 多路调度节点故事

```
作为 多路调度节点
在 用户启动多路对比时
为了 同一用例 N 路并发跑
我需要：

【上下文信息】
- 各路通道配置（BaseURL/Key/协议/Headers）
- 各路模型 v2 基线 rate_limits（限速口径）
- 全局统一超参

【能力支持】
- 并发调用（Promise.all）
- 限速节流（并发数 vs RPM/TPM）
- 轮询聚合

【约束条件】
- 最少 2 路、最多 4 路
- 限速口径不同的通道间不横比数值
- Key 不出浏览器
```

**为什么需要这些**：五家限速口径三家不同，不节流会触发限流。

### 4.3 用例生成节点故事

```
作为 用例生成节点（v2.0 落地）
在 客户提交测试标准时
为了 产出结构化用例
我需要：

【上下文信息】
- 客户标准（结构化表 + 自然语言）
- 目标模型 v2 基线（含 important_alignment_findings）
- 四类对齐维度模板（A/B/C/D）

【能力支持】
- LLM 理解客户标准
- 基线驱动 expected
- refs 自动关联

【约束条件】
- 只用基线字段，禁止编造
- 未公布项判 INC，不支持项判 SKIP
- 每条必带 refs
```

**为什么需要这些**：用例生成是核心增量，必须受基线约束否则跑不通。

### 4.4 安全节点故事

```
作为 安全节点
在 全程 Key 处理时
为了 Key 不泄露
我需要：

【上下文信息】
- 用户输入的各路 API Key

【能力支持】
- localStorage/内存存储
- 密码框明文/隐藏切换

【约束条件】
- 不上传后端
- 不写日志
- 不 console.log 敏感字段
- 不自造鉴权（沿用 window.AUTH_TOKEN）
```

**为什么需要这些**：Key 是敏感凭证，泄露即风险。

### 4.5 节点故事 vs 技术实现

| 节点故事需求 | 技术实现 |
|---|---|
| 上下文信息 | 源码/数据样本/基线 JSON |
| 能力支持 | React/Vue 组件、fetch、Promise.all |
| 约束条件 | 提示词约束、代码逻辑、CSS 变量 |

### 4.6 节点故事的核心价值

- **对 AI 生成工具**：明确各节点需哪些上下文、受什么约束。
- **对验收者**：明确验收标准。
- **对开发团队**：理解生成产物的结构。

## 5. 生成旅程

### 5.1 完整生成六阶段

#### 阶段 1：喂料准备（0-1）
- 整理物料：源码、数据样本、基线、PRD、拆解报告。
- 确定喂料顺序：主规格→源码→JSON→PRD→基线。

#### 阶段 2：复刻生成（1-2）
- 喂 `llm_console.html` + 两份 JSON。
- 生成三 Tab + 验证卡 + 四态 + 轮询。

#### 阶段 3：后端对接（2-3）
- 直连 /api/plan、/api/runs。
- 验证真实拉到 27 用例与 run 结果。

#### 阶段 4：增量1 多路对比（3-4）
- 生成多路工作台 + 并发调度 + 对比表。

#### 阶段 5：增量2 用例生成（4-5）
- 生成用例生成器面板 + 四类对齐维度模板。

#### 阶段 6：验收（5-6）
- 按验收标准逐项核对。

### 5.2 生成设计原则

1. **复刻优先**：先 1:1 还原，再加增量。
2. **喂料有序**：主规格最前，附件随后。
3. **约束明确**：关键前提 AI 必须遵守。
4. **安全贯穿**：Key 处理全程约束。

## 6. 工作流设计

### 6.1 传统开发 vs AI 生成

| 环节 | 传统开发 | AI 生成 |
|---|---|---|
| UI | 逐页面设计 | 喂源码复刻 |
| 对接 | 逐接口联调 | 喂契约直连 |
| 增量 | 需求拆解开发 | 提示词驱动生成 |
| 验收 | 人工 | 按验收标准核对 |

### 6.2 生成工作流

```
喂料 → 复刻节点(源码+JSON) → 后端对接(契约)
  → 多路调度节点 → 用例生成节点 → 安全节点贯穿 → 验收
```

### 6.3 各节点职责

| 节点 | 职责 | 阶段 |
|---|---|---|
| 复刻 | 1:1 还原 | 阶段2 |
| 后端对接 | 直连 API | 阶段3 |
| 多路调度 | 并发+节流 | 阶段4 |
| 用例生成 | 客户标准→用例 | 阶段5 |
| 安全 | Key 约束 | 贯穿 |
| 验收 | 核对标准 | 阶段6 |

### 6.4 关键时序

#### 6.4.1 复刻生成时序
```
喂主规格→喂llm_console.html→喂bench_plan.json+bench_runs.json
  →生成三Tab+验证卡→对接/api/plan+/api/runs→验证真实数据
```

#### 6.4.2 增量生成时序
```
喂增量规格→喂v2基线→生成多路工作台→生成用例生成器
  →喂四类对齐维度→验证增量功能
```

## 8. 提示词设计

### 8.1 一句话生成指令

> 做一个纯前端 Web 应用，**1:1 复刻 `http://120.92.93.22/llm-benchmark` 的验收控制台**（三Tab、验证卡、PASS/FAIL/INC/SKIP），并叠加两个增量：**①多路 Endpoint 并排对比**（前端并发调用、聚合对比）**②按客户测试标准生成新用例**。前端直连公司现有后端 API（`/api/plan`、`/api/runs`），**不新建任何后端**。所有功能依据见同目录《PRD》与《参考网站拆解报告》。

### 8.2 生成策略

#### 策略 1：关键前提（AI 必须遵守）
1. **纯前端**：React 或 Vue 均可。无后端代码，不引入数据库。
2. **直连现有后端**：用公司现有 API，绝不新建后端。
3. **API Key 仅存浏览器**（localStorage/内存），不上传，不写日志。密码框明文/隐藏切换。
4. **复刻 + 增量**：先 1:1 还原全部 UI/交互，再加两个增量。复刻时不擅自改设计。

#### 策略 2：复刻形态明确
- 顶部三 Tab + hash 路由。
- 发起测试页：模型级联（厂商→系列→版本）+ 基线展示 + 参数（协议/profile/限速覆盖）+ Key/Endpoint/Headers。
- 进行中 5s 轮询 `/api/runs`。
- 卡片网格 + 计数徽章 + 验证卡分组。

#### 策略 3：契约直连
- GET `/api/plan` → 27 用例（字段见 §9.3）。
- GET/POST `/api/runs` → run 结果（字段见拆解报告 §7.4）。
- 读接口公开，写操作沿用 `window.AUTH_TOKEN`。

#### 策略 4：基线增强
- 用 v2 基线（39 模型）替代简版 CATALOG。
- 每版本挂 baseline 指针（temp/top_p 范围、功能开关、官网来源、价格、NOT_PUBLISHED）。

#### 策略 5：增量约束
- 多路：2-4 路，全局统一超参，限速节流按各家口径。
- 用例生成：四类对齐维度模板，基线驱动 expected，未公布→INC，不支持→SKIP。

### 8.3 喂料顺序

| 顺序 | 文件 | 喂什么 |
|---|---|---|
| 1 | 本主规格 | 生成蓝图 |
| 2 | `llm_console.html` | 参考站点前端源码（UI/交互/CSS 1:1） |
| 3 | `bench_plan.json` | 27 用例（数据契约样本） |
| 4 | `bench_runs.json` | run 结果（数据契约样本 + mock） |
| 5 | PRD | 功能需求与原则 |
| 6 | 拆解报告 | 站点架构与复用点 |
| 7 | `baselines/v2/*.json` | 五家 v2 基线（标准数据） |

> 把本主规格放最前，其余作附件；让 AI 先读主规格与 `llm_console.html`、两份 JSON，再读 PRD 与基线。

### 8.4 风格差异化

| 生成场景 | 策略 |

## 9. 数据集要求

### 9.1 CATALOG（模型树），用增强版

参考站点 CATALOG 较简；用 v2 基线补全后构建，结构保持：
```json
[{ "id":"zhipu","name":"智谱","series":[{ "id":"glm-5","name":"GLM-5系列",
   "versions":[{ "id":"glm-5.2","name":"GLM-5.2",
     "protocols":["openai"], "maxOutput":131072, "rpm":500, "tpm":1000000 }] }] }, ...]
```
增强：每版本挂 `baseline` 指针（temp/top_p 范围、功能开关、官网来源、价格、NOT_PUBLISHED）。

### 9.2 官方参数基线，`baselines/v2/*.json`（5 家，已就绪）

- `kimi.json / deepseek.json / zhipu.json / minimax.json / mimo.json`，39 模型。
- 每条带 `sources`（官网 URL）、`verification_notes`、`important_alignment_findings`。
- 官网未公布标 NOT_PUBLISHED。
- 用法：选模型渲染基线；驱动用例 expected；未公布项显示⚠️不测。

### 9.3 标准用例，`bench_plan.json`（27 条，已就绪）

直接用 `/api/plan` 拉取或前端内置兜底。字段：id/group/priority/profiles/name/desc/requirement/expected/run/refs。含 expected/requirement/refs。

### 9.4 实测样本，`bench_runs.json`（3 个真实 run，已就绪）

开发期作 mock，验证渲染逻辑。字段：run_id/metadata/counts/running/returncode。

### 9.5 数据收集策略

- 基线：WebFetch 抓官网 + bundle 逆向 + 控制台补全（已完成五家 v2）。
- 用例：/api/plan 拉取。
- run：真实轮询 /api/runs 或本地 serve.py 真发。

## 10. 测试标准

### 10.1 复刻验收

1. 1:1 复刻三 Tab + 验证卡 + 四态徽章 + 进行中轮询。
2. 直连 `/api/plan` `/api/runs`，真实拉到 27 用例与 run 结果。

### 10.2 增量验收

3. 多路工作台：≥2 路独立配置，并发跑，出多路对比表。
4. 客户标准生成器：能输入标准、产出结构化用例并入树。
5. 各模型基线各自独立展示，官网未公布项显示⚠️不测。

### 10.3 性能

- 轮询不阻塞 UI。
- 基线加载 ≤1s。
- 多路并发用 Promise.all。

### 10.4 安全

6. API Key 仅存浏览器，不上传，不写日志。

## 11. 异常处理与降级策略

### 11.1 异常场景

| 场景 | 降级 |
|---|---|
| 后端不可达 | 退回本地 serve.py 真发或 mock |
| GitHub Pages 无代理 | 自动退回模拟演示，不报错 |
| 限流 | 按基线口径节流重试 |
| Key 无效 | 标该路异常，不阻塞其他路 |
| 基线未公布 | 判 INC，不编造 |
| 参数不适用 | 判 SKIP |

### 11.2 降级流程
```

```
